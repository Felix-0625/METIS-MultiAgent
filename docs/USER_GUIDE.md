# METIS 使用指南

## 1. 系统定位

METIS 将需求、规划、执行、质检、返工和签收组织为可恢复的多 Agent 交付流程。

核心原则：

- 服务端状态为准。
- 计划确认后再执行。
- 文件交付可追踪。
- 质量门禁不可跳过。
- Final QA 与最终签收分离。

架构、接口、部署和安全细节分别见：

- [系统架构](ARCHITECTURE.md)
- [接口文档](API.md)
- [部署指南](DEPLOYMENT.md)
- [安全策略](../SECURITY.md)

## 2. 快速开始

### 2.1 环境要求

| 组件 | 要求 |
|---|---|
| Python | 3.10+ |
| Node.js | 18+ |
| npm | 9+ |
| 数据库 | SQLite（本地）或 PostgreSQL（生产） |

### 2.2 安装

```powershell
Copy-Item .env.example .env

python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend\requirements.txt

Set-Location frontend
npm ci
```

编辑 `.env`，至少配置：

```dotenv
HERMES_API_URL=https://example.com/v1
HERMES_API_KEY=<your-key>
ADMIN_USERNAME=admin
ADMIN_PASSWORD=<strong-password>
```

禁止提交 `.env`、API Key、数据库连接串或生产密码。

### 2.3 启动

后端：

```powershell
Set-Location backend
python main.py
```

前端：

```powershell
Set-Location frontend
npm run dev
```

默认地址：

| 服务 | 地址 |
|---|---|
| 前端 | `http://localhost:3000` |
| 后端 | `http://localhost:8000` |
| API 文档 | `http://localhost:8000/docs` |
| 健康检查 | `http://localhost:8000/health` |

## 3. 首次配置

1. 使用管理员账号登录。
2. 打开“设置”。
3. 配置模型供应商、API 地址、模型和参数。
4. 执行连接测试。
5. 打开“资源中心”，检查成员池、专家池和技能池。

浏览器使用 HttpOnly Cookie 保存会话。API Key 仅在设置页录入，查询接口返回掩码值。

## 4. 标准交付流程

```text
想法落地
  → 总体规划
  → 阶段规划
  → Agent 执行
  → Pre-QA
  → Supervisor QC
  → 阶段确认
  → Final QA
  → Signoff
```

### 4.1 想法落地

1. 新建对话。
2. 描述目标、用户、范围和约束。
3. 按阶段补全需求。
4. 生成并确认需求文档。

需求文档由服务端保存。修改后会产生新修订版本。

### 4.2 总体规划

1. 创建项目。
2. 与 PM 团队沟通。
3. 收集分析并生成总计划。
4. 检查阶段目标、依赖和验收标准。
5. 确认计划。

确认后的计划是阶段规划的权威来源。

### 4.3 阶段规划

1. 进入阶段看板。
2. 由阶段 PM 生成任务计划。
3. 检查任务、专家、执行角色、技术要求和依赖。
4. 确认专家仍可用。
5. 启动阶段。

任务与专家一一绑定。专家池发生相关变更后，需要重新校验阶段计划。

### 4.4 执行与交付

- Agent 按依赖顺序执行。
- 每个任务只能修改授权路径。
- 文件记录创建者、责任人、哈希和修改历史。
- WebSocket 负责变化通知，页面通过 HTTP 获取最终状态。
- 异步任务必须等待明确终态。

执行失败时优先查看运行记录、任务错误和阶段问题，不要重复点击启动。

### 4.5 Pre-QA 与 QC

Pre-QA 检查构建、测试、依赖、路径和交付合同。通过后，Supervisor 使用绑定文件和验收标准的 QC 审查包进行检查。

发现问题时：

1. 确认问题归属。
2. 启动自动返工。
3. 等待完整返工批次结束。
4. 重新验证。
5. 无阻塞问题后确认阶段完成。

### 4.6 Final QA 与签收

所有阶段完成后：

1. 启动 Final QA。
2. 等待质量检查和运行验收结束。
3. 处理全部阻塞项。
4. 检查签收状态。
5. 执行 Signoff。

Final QA 通过不代表项目已签收。当前文件、运行证据或交付文档变化后，需要重新验收。

## 5. 功能入口

| 功能 | 用途 |
|---|---|
| 想法落地 | 需求澄清与文档生成 |
| 项目列表 | 创建、查看和管理项目 |
| PM 团队 | 总体规划与需求调整 |
| 阶段看板 | 阶段规划、执行、QC 和返工 |
| 进度视图 | Agent、任务和阶段状态 |
| 文件浏览器 | 文件、版本、下载和归档 |
| 资源中心 | 成员、专家和技能 |
| 设置 | 模型与 API 配置 |
| 工程师入口 | 人工接管和精准修复 |

## 6. 文件与版本

- 文件路径必须位于项目工作区。
- 任务不得覆盖无权限文件。
- 依赖任务修改文件前必须读取完整当前版本。
- 项目归档必须通过服务端下载。
- 回滚后应重新运行相关质量门禁。

## 7. 账号与权限

- 普通用户只能访问自己的项目和资源池。
- 管理员可管理用户。
- 修改密码后旧令牌失效。
- WebSocket 同样校验用户和项目归属。
- 不共享管理员账号或浏览器会话。

## 8. 常见问题

### 登录后出现 401

确认前后端域名和 `CORS_ORIGINS`，清除旧 Cookie 后重新登录。

### 模型连接失败

检查 API 地址、模型名、Key、代理和供应商兼容参数；不要在日志中粘贴完整 Key。

### 阶段无法启动

检查总计划、阶段计划、专家状态、资源池版本、任务依赖和文件锁。

### 自动返工一直运行

查看返工状态和最新阻塞项。只有相同阻塞连续重复才属于无进展。

### Final QA 已通过但不能签收

检查运行验收、当前文件哈希、交付文档和开放返工。Final QA 与 Signoff 是独立门禁。

### 页面没有及时更新

WebSocket 可能断线。页面会回退到 HTTP 轮询；刷新后以服务端状态为准。

### Railway 部署失败

检查 `DEPLOYMENT.md` 中的 Dockerfile、`PORT`、PostgreSQL、Volume、环境变量和 `/health` 配置。

## 9. 使用边界

- 不把 HTTP 200 当作工作流完成。
- 不用固定等待时间代替终态检查。
- 不绕过 Pre-QA、QC、Final QA 或 Signoff。
- 不在共享生产环境直接运行未知生成代码。
- 不把临时测试产物纳入正式交付。
